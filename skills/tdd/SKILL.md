# 测试驱动开发（TDD）

## 红-绿-重构循环

1. **红**：为期望行为先写一个**失败**的测试（用 `test_run` 确认它在红——真的失败且失败原因正确）。
2. **绿**：用最小实现让测试通过（可以写得丑，先绿）。
3. **重构**：在测试保护下清理实现与测试（`checkpoint_create` 留后路；每步 `test_run` 确认仍绿）。

## 规则

- 一次只写一个测试，从最核心的行为开始；先测行为，再测边界。
- 测试要**独立、快速、可重复**；不要依赖网络/真实数据库（除非集成测试明确）。
- 命名：`should 描述行为 when 前提`（如 `should return 400 when body missing`）。
- 每个循环都要 `test_run` 验证，红绿状态都要确认，不要跳过。
- 覆盖边界：空输入、最小值、异常、并发（如适用）。

## 配合本环境的工具

- `test_run` 运行测试（自动探测 npm/pytest/cargo/go 测试命令）
- `changeset_review` 整理测试+实现的改动
- `checkpoint_create` 重构前快照

## 交付标准

- 功能实现 + 对应测试一起交付；`test_run` 全绿；`git_diff` 复查没有多余改动。
