# 代码审查

## 流程

1. **先看改动范围**：用 `git_status`（分支+变更清单）和 `changeset_status`（每文件增删行）了解改动面；需要时 `git_diff` 看完整 diff（`staged` 看已暂存）。
2. **按维度审查**（逐文件）：
   - **正确性**：边界条件、空值/异常路径、并发/异步时序、类型与隐式转换
   - **安全**：注入（命令/路径/SQL）、敏感信息泄漏、权限校验缺失、不可信输入
   - **风格与可维护性**：命名、重复代码、魔法数、过深嵌套、注释是否解释了"为什么"
   - **测试**：改动是否有对应测试？边界用例覆盖了吗？
3. **用上下文判断**：`semantic_search "<相关概念>"` 查调用方/相关实现；`memory_read` 读项目约定；`git_log` 看改动意图与历史。
4. **输出结构化报告**：
   - 严重问题（必须修）：文件:行 + 问题 + 建议
   - 一般问题（建议修）：同上
   - 亮点（可保留）
   - 总结论：通过 / 需修改后通过

## 原则

- 先确认"这个改动想解决什么"再判断是否合理（用 `git_log` 或问用户）。
- 每个问题给出**可执行的修改建议**，不要只说"有问题"。
- 审查你自己刚写的代码时，先 `git_diff` 全量过一遍再交付。
