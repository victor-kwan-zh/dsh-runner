# 系统化调试

## 闭环流程

1. **复现**：先稳定复现问题。问清楚触发条件或自己构造最小复现；用 `test_run`（或手写最小脚本）跑出失败。
2. **定位**：不要猜，二分定位——
   - 先看错误堆栈/日志的**第一条**真实原因（不是外层包装）
   - 用 `semantic_search "<报错关键词/疑似模块>"` 找到相关代码
   - 缩小范围：注释/还原一半改动，或对输入做二分
3. **假设-验证**：每条假设都要能用一个实验证实/证伪（加日志、写断言、跑单测）。
4. **修复**：最小改动，不留无关重构；先 `checkpoint_create`（改动前留后路）。
5. **验证**：`test_run` 全量测试 + 复现用例确认通过；确认没有回归（`git_diff` 复查）。

## 反模式（避免）

- ❌ 看到错误就乱改、加随机 try/catch 吞异常
- ❌ 一次改多个地方，不知道哪个生效
- ❌ 修复后不跑测试就交付
- ❌ 只修表象，不查根因（如只改报错文案）

## 提速技巧

- 失败用例先固定下来（写成测试），再开始修——修到它通过 = 问题解决。
- 排查时优先 `git_log`/`git_blame`（git blame 可用 `git_log` + 文件历史代替）看最近改动。
